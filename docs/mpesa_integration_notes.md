# M-Pesa / *334# / M-Pesa app integration notes

The backend already has Daraja-style STK Push and B2C calls and callback endpoints. The missing piece is the provider-side onboarding required to expose a service through Safaricom-controlled customer channels.

## What this backend can do

- initiate an STK payment for an order
- receive and reconcile the STK callback
- hold the payment in the internal ledger
- generate a three-hour delivery QR
- initiate B2C release/refund after the delivery event
- reconcile B2C callbacks
- expose `/ussd/callback` for an approved USSD gateway

## What requires Safaricom/provider onboarding

- production Daraja credentials and shortcode configuration
- production callback URLs and security/network controls
- B2C permissions/initiator configuration
- any approved USSD service code/menu integration
- any approved M-Pesa app product/deep-link/menu integration
- commercial/safeguarding arrangements for a customer-funds/escrow product

Do not represent the application as being inside the official M-Pesa app or `*334#` until the corresponding Safaricom product and integration has been approved and provisioned.

## Callback security

Set `MPESA_CALLBACK_SECRET` to a long random secret. Callback URLs contain no authentication secret, for example:

`https://your-domain.example/mpesa/stk-callback`

## Callback authentication

The application requires the `X-Mpesa-Secret` HTTP header on STK, B2C, and B2C timeout callbacks. The secret is never accepted through a query parameter or embedded in the callback URL. Because Daraja does not provide a configurable custom callback header, put a trusted reverse proxy/API gateway in front of these endpoints to inject the header after applying your provider-facing access controls. Do not expose the application directly to untrusted callers with a static secret header.

## Buyer QR delivery

Set `BUYER_PORTAL_BASE_URL` to the public buyer web/app origin. After payment confirmation the STK callback sends the buyer a short-lived QR-view URL. The buyer application can alternatively use `X-Buyer-Access-Token` with the buyer API endpoint.

## Callback authentication note

The application accepts `X-Mpesa-Secret` for direct/internal callback requests. Daraja itself does not provide a configurable custom callback authentication header, so provider-facing URLs generated by `callback_url()` use fixed `/mpesa/...` paths. The application authenticates callbacks with the `X-Mpesa-Secret` header (typically injected by a trusted reverse proxy/gateway). Query-string callback secrets are not accepted.

For a production deployment, an ingress/reverse proxy can expose a stable public callback endpoint, validate the provider-facing route/IP policy, inject `X-Mpesa-Secret`, and forward the request to the application. Do not log the secret-bearing path at INFO level, and use HTTPS everywhere.

## USSD / M-Pesa app product integration

The backend can expose a USSD callback contract, but it cannot modify Safaricom's native `*334#` menu by itself. A dedicated USSD service/short code and provider onboarding are required unless Safaricom explicitly provisions the service in its own channel.

Likewise, the backend cannot insert a custom feature into the native M-Pesa app UI by code alone. Any M-Pesa app discovery/mini-app programme, SDK, review process, eligibility and menu placement must be confirmed against Safaricom's current partner/developer programme before implementation is treated as guaranteed.


## Callback authentication deployment requirement

Callback endpoints authenticate with `X-Mpesa-Secret`; the secret is never embedded
in the Safaricom callback URL. Safaricom/Daraja does not provide a way for this
application to tell it to send an arbitrary custom authentication header, so place
a trusted reverse proxy/API gateway in front of the callback endpoints and have
that gateway inject `X-Mpesa-Secret` on the upstream request. Do not put the secret
in a query string or URL path.
